# Berserk VPN Bot v6.2.0 — Catalog & Provider Core

ربات تلگرام فروش VPN با کاتالوگ دسته‌بندی‌شده، فروش استخری، ساخت خودکار سرویس از تأمین‌کننده و پنل مدیریت قابل‌چیدمان.

این نسخه ساختار اصلی **۲۲ فایلی** پروژه را حفظ می‌کند. تغییر اصلی v6.2 این است که «فروشگاه»، «پلن»، «روش خرید» و «تأمین‌کننده سرویس» از هم جدا شده‌اند؛ بنابراین رابط مشتری به یک پنل خاص وابسته نیست و در آینده می‌توان Adapter پنل‌های دیگری را بدون بازنویسی کیف پول و مسیر خرید اضافه کرد.

---

## قابلیت‌های اصلی v6.2

- دسته‌بندی واقعی پلن‌ها، مانند `💎 VIP` و `🌱 اقتصادی`
- مسیر مشتری: `خرید سرویس → دسته → پلن → خرید`
- ساخت و ویرایش یکپارچه پلن؛ حجم و مدت فقط یک بار وارد می‌شوند
- چهار حالت خرید برای هر پلن:
  - `direct` خرید مستقیم یک سرویس
  - `quantity` انتخاب تعداد
  - `wholesale` فقط هماهنگی عمده
  - `disabled` غیرفعال
- دو مدل تحویل فعلی:
  - `pool` تحویل از استخر لینک آماده
  - Provider ساخت خودکار، فعلاً Adapter رسمی داخلی `YouPanel`
- معماری Provider قابل توسعه برای پنل‌های بعدی
- نمایش اکانت تست داخل کاتالوگ خرید
- بخش مستقل مدیریت اکانت‌های تست در ادمین
- چیدمان منوی اصلی کاربر و داشبورد ادمین با بالا/پایین
- اجرای واقعی جایگاه دکمه‌ها در منوی اصلی، خرید، کیف پول، آموزش، پشتیبانی و سرویس‌های من
- ادغام گزینه‌های تکراری لینک‌ها در بخش واحد `استخر لینک‌ها`
- انتقال تست اتصال YouPanel به `تأمین‌کننده‌ها → YouPanel`
- حفظ کامل دیتابیس، خریدها، لینک‌های استخری و پلن‌های نسخه‌های قبلی

## هشدار امنیتی

اطلاعات زیر را هرگز داخل سورس، GitHub، README، لاگ یا پیام تلگرام قرار ندهید:

- رمز پنل
- JWT / Bearer Token
- توکن ربات
- Cookie یا Session
- لینک اشتراک واقعی مشتری

اطلاعات محرمانه فقط در Railway Variables نگهداری شوند. JWT پنل فقط در حافظه Process نگهداری می‌شود و وارد SQLite یا بک‌آپ نمی‌شود.

اگر توکن یا رمز قبلاً منتشر شده است، رمز را تغییر دهید و نشست‌های قبلی را باطل کنید.

## نصب روی Railway

### متغیرهای اصلی

```env
BOT_TOKEN=YOUR_TELEGRAM_BOT_TOKEN
ADMIN_ID=YOUR_TELEGRAM_ADMIN_ID
OWNER_ID=YOUR_TELEGRAM_OWNER_ID
ADMIN_COMMAND=YOUR_SECRET_ADMIN_COMMAND
DB_PATH=/data/berserk.db
```

برای چند ادمین، آیدی‌ها را با کاما جدا کنید:

```env
ADMIN_ID=111111111,222222222
```

برای ماندگاری دیتابیس، Railway Volume بسازید و `DB_PATH` را داخل Volume قرار دهید. فایل دیتابیس فعلی را هنگام جایگزینی سورس حذف یا overwrite نکنید.

### متغیرهای عمومی پیشنهادی

```env
BROADCAST_DELAY=0.08
REF_REWARD=30000
MAX_TOTAL_REFERRALS=50
MAX_REFERRALS_PER_DAY=10
BACKUP_INTERVAL_SECONDS=86400
BACKUP_RETENTION_COUNT=30
```

## اتصال تأمین‌کننده YouPanel

YouPanel در v6.2 یک Adapter از سیستم عمومی Provider است؛ یعنی پلن‌های فروشگاه با `provider_key` به تأمین‌کننده متصل می‌شوند و منطق خرید به نام YouPanel گره نخورده است.

### متغیرهای اتصال

```env
YOUPANEL_BASE_URL=https://panel.example.com:2053
YOUPANEL_USERNAME=panel_admin_username
YOUPANEL_PASSWORD=panel_admin_password
YOUPANEL_TIMEOUT_SECONDS=20
YOUPANEL_VERIFY_SSL=true
YOUPANEL_INBOUNDS_JSON={"vless":["RTL-1","VLESS + WS","tcp","TUN"]}
```

آدرس پایه نباید `/dashboard` یا `/api` داشته باشد. نام inboundها باید دقیقاً با پنل برابر باشند.

### APIهای استفاده‌شده توسط Adapter فعلی

```text
POST   /api/admin/token
POST   /api/user
PUT    /api/user/{username}
DELETE /api/user/{username}
GET    /api/user/{username}/usage?start=...
POST   /api/user/{username}/reset
POST   /api/user/{username}/revoke_sub
GET    /api/admin
```

API مشاهده‌شده داخلی پنل است و ممکن است پس از ارتقای پنل تغییر کند. بعد از هر آپدیت YouPanel ابتدا در محیط تست، `تأمین‌کننده‌ها → YouPanel → تست اتصال` را اجرا کنید.

## تنظیم اکانت تست

نام‌های عمومی v6.2 در اولویت‌اند و نام‌های قدیمی YouPanel برای سازگاری باقی مانده‌اند:

```env
TRIAL_PROVIDER_KEY=youpanel
TRIAL_ENABLED=true
TRIAL_SIZE_MB=200
TRIAL_DAYS=1
TRIAL_MAX_DEVICES=1
```

اگر این متغیرها تعریف نشوند، پیش‌فرض پروژه ۲۰۰ مگابایت، یک روز، یک دستگاه و شروع از اولین اتصال است.

نام‌های قدیمی زیر هنوز پذیرفته می‌شوند:

```env
YOUPANEL_TRIAL_ENABLED=true
YOUPANEL_TRIAL_SIZE_MB=200
YOUPANEL_TRIAL_DAYS=1
YOUPANEL_TRIAL_MAX_DEVICES=1
```

هر Telegram ID فقط یک تست موفق دریافت می‌کند. تست ناموفق قابل Retry است.

## معماری کاتالوگ

### دسته‌ها

هر دسته شامل این تنظیمات است:

- عنوان و ایموجی
- توضیح
- ترتیب نمایش
- فعال/غیرفعال
- مخاطب: همه، خریداران، بدون خرید، دارای/بدون سرویس، کاربران عادی، کاربران تست یا فقط ادمین‌ها
- تاریخ شروع و پایان اختیاری

نمونه:

```text
💎 VIP
🌱 اقتصادی
```

### پلن‌ها

هر پلن مستقل از دسته و روش تحویل، اطلاعات مشترک زیر را دارد:

- دسته
- عنوان
- حجم
- مدت
- قیمت
- توضیح
- برچسب
- ترتیب نمایش
- وضعیت
- حداکثر خرید
- حد هشدار
- متن قبل و بعد خرید
- نحوه خرید
- روش تحویل / Provider

دسته با روش تحویل یکی نیست. برای مثال یک پلن VIP می‌تواند استخری یا پنلی باشد و یک پلن اقتصادی هم می‌تواند از هر تأمین‌کننده‌ای تحویل شود.

## مسیر ساخت پلن

مسیر ادمین:

```text
پنل مدیریت
→ 📦 کاتالوگ و فروش
→ 🏷 پلن‌ها
→ ➕ ساخت پلن
```

ویزارد یکپارچه:

```text
۱. انتخاب دسته
۲. عنوان
۳. حجم
۴. مدت
۵. قیمت
۶. نحوه خرید
۷. روش تحویل
۸. تنظیم تکمیلی منبع، در صورت نیاز
۹. تعداد دستگاه و شروع اعتبار، برای Providerهای پشتیبانی‌شده
۱۰. توضیح
۱۱. پیش‌نمایش و ذخیره
```

حجم و مدت دوباره پرسیده نمی‌شوند. برای Provider، همان مقادیر عمومی به byte و second تبدیل می‌شوند.

## روش‌های خرید هر پلن

### خرید مستقیم (`direct`)

- فقط یک سرویس خریداری می‌شود
- مرحله انتخاب تعداد حذف می‌شود
- مناسب سرویس اختصاصی یا پلن‌های شخصی

### انتخاب تعداد (`quantity`)

- دکمه‌های تعداد تا سقف پلن نشان داده می‌شوند
- مناسب استخر لینک یا خرید چند سرویس

### عمده (`wholesale`)

- خرید خودکار بسته است
- کاربر به هماهنگی پشتیبانی/عمده هدایت می‌شود

### غیرفعال (`disabled`)

- پلن در فروشگاه قابل خرید نیست

---

## روش‌های تحویل

### استخر (`pool`)

- لینک‌ها پیش از فروش به همان پلن وارد می‌شوند
- تخصیص لینک و کسر کیف پول اتمیک است
- لینک تکراری وارد نمی‌شود
- لینک تحویل اشتباه قابل بازگردانی به همان استخر است

### تأمین‌کننده (`provider`)

- سرویس پس از پرداخت ساخته می‌شود
- هر خرید یک provider key ذخیره می‌کند
- در موفقیت، subscription URL ذخیره و تحویل می‌شود
- در شکست، ساخت‌های نیمه‌کاره best-effort پاک و مبلغ Refund می‌شود
- سفارش provisioning قدیمی پس از Restart بازیابی می‌شود

Providerهای ثبت‌شده از طریق Registry در `subs.py` مدیریت می‌شوند. افزودن پنل جدید باید با پیاده‌سازی Interface مشترک انجام شود، نه با تغییر مستقیم مسیر خرید و کیف پول.

## دیتابیس و Migration

Schema نسخه حاضر:

```text
620
```

جدول‌ها/فیلدهای مهم جدید:

- `plan_categories`
- `admin_menu_items`
- `plans.category_id`
- `plans.purchase_mode`
- `plans.provider_key`
- `plans.provider_options_json`
- `trial_claims.provider_key`

Migration پلن‌های قدیمی:

- عنوان دارای VIP/ویژه → دسته VIP
- عنوان دارای اقتصادی/economic → دسته اقتصادی
- سایر پلن‌ها → دسته سرویس‌ها
- `delivery_type=youpanel` به provider key مربوطه منتقل می‌شود
- فروش استخری و خریدهای قبلی حفظ می‌شوند

قبل از Deploy از دیتابیس فعلی بک‌آپ بگیرید. Restore بک‌آپ با Schema جدیدتر از سورس فعلی رد می‌شود.

## محدودیت‌های فعلی

- Provider عملیاتی موجود فعلاً YouPanel است؛ معماری برای Adapterهای بعدی آماده شده است.
- پروژه روی `aiogram 2.25.1` و Python 3.11 اجرا می‌شود.
- SQLite برای یک Instance مناسب است؛ اجرای چند Replica هم‌زمان به PostgreSQL نیاز دارد.
- بدون API پنل، مصرف واقعی و اولین اتصال سرویس‌های استخری قابل تشخیص نیست.
- `admin.py` و `db.py` به‌دلیل قانون حفظ ساختار ۲۲ فایلی همچنان بزرگ‌اند؛ شکستن آن‌ها باید در نسخه معماری جدا انجام شود.
