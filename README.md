# Berserk VPN Bot v6.0.0

ربات تلگرام فروش و توزیع ساب‌لینک آماده VPN از استخر لینک‌ها، با کیف پول، پرداخت کارت‌به‌کارت، مدیریت چندپلنی، پنل ادمین، تیکت، رفرال، بک‌آپ و کنترل کاربران تست.

این نسخه یک **Code Audit & Clean Release** است. ساختار اصلی ۲۲ فایلی پروژه حفظ شده، اما مسیرهای حساس مالی، دیتابیس، بک‌آپ، خرید، رفرال، FSM و اکانت تست بازبینی و تمیز شده‌اند.

---

## نصب سریع روی Railway

متغیرهای محیطی ضروری:

```env
BOT_TOKEN=توکن ربات از BotFather
ADMIN_ID=آیدی عددی ادمین یا چند آیدی جداشده با کاما
ADMIN_COMMAND=دستور مخفی پنل مدیریت
DB_PATH=/data/berserk.db
```

متغیرهای پیشنهادی:

```env
OWNER_ID=آیدی مالک اصلی برای عملیات حساس مثل Restore
BROADCAST_DELAY=0.08
REF_REWARD=30000
MAX_TOTAL_REFERRALS=50
MAX_REFERRALS_PER_DAY=10
BACKUP_INTERVAL_SECONDS=86400
BACKUP_RETENTION_COUNT=30
```

برای استفاده دائمی، Railway Volume بسازید و `DB_PATH` را روی مسیر Volume قرار دهید. بدون Volume، دیتابیس ممکن است بعد از Redeploy از بین برود.

Runtime پروژه:

```txt
Python 3.11.9
aiogram 2.25.1
SQLite
```

## معماری پروژه

ساختار ۲۲ فایلی برای سازگاری با نسخه‌های قبلی حفظ شده است.

```txt

db.py           Schema، migration، queryها و تراکنش‌های اصلی
wallet.py       شارژ کیف پول، رسید و تأیید پرداخت
subs.py         استخر لینک‌ها و بازگردانی سرویس
backup.py       ساخت، اعتبارسنجی و Restore بک‌آپ
fsm_storage.py  ذخیره پایدار FSM در SQLite
messages.py     قالب‌های قابل ویرایش و تقسیم امن پیام‌ها
menus.py        کیبوردهای کاربر و override دکمه‌های سیستمی
tickets.py      پشتیبانی و تیکت‌ها

anti_fraud.py   کنترل‌های ضدتقلب رفرال
```

### بدهی فنی باقی‌مانده

به‌دلیل الزام حفظ همین ۲۲ فایل، `admin.py` و `db.py` همچنان بزرگ هستند. برای رشد خیلی بیشتر پروژه، شکستن آن‌ها به ماژول‌های کوچک‌تر توصیه می‌شود؛ اما این کار عمداً در v6.0.0 انجام نشده تا migration و deploy فعلی کم‌ریسک بماند.

## جریان خرید

```txt
خرید سرویس
→ انتخاب پلن
→ انتخاب تعداد
→ بررسی فعال بودن پلن و سقف تعداد
→ بررسی موجودی لینک همان پلن
→ بررسی کیف پول
→ خرید اتمیک و تحویل لینک
```

اگر موجودی کیف پول کافی نباشد:

```txt
انتخاب تعداد
→ محاسبه کسری
→ نمایش شماره کارت و مبلغ دقیق
→ ارسال رسید
→ تأیید ادمین
→ شارژ کیف پول
→ تلاش برای تکمیل خودکار همان خرید
```

اگر بعد از پرداخت موجودی لینک کافی نباشد، پول در کیف پول کاربر می‌ماند و خرید ناقص دوباره از حساب او کسر نمی‌شود.

## قواعد استخر لینک‌ها

- هر لینک دقیق فقط یک بار در دیتابیس نگهداری می‌شود.
- فروش از موجودی آزاد همان `plan_id` انجام می‌شود.
- تخصیص لینک و کسر کیف پول داخل یک تراکنش انجام می‌شود.
- در خرید هم‌زمان، یک لینک نباید به دو کاربر تحویل شود.
- بازگردانی به استخر همان رکورد را آزاد می‌کند و لینک جدید تکراری نمی‌سازد.
- سرویس تحویل‌شده بدون عملیات صریح ادمین حذف نمی‌شود.

هنگام ورود دسته‌ای لینک‌ها، حتماً پلن مقصد را درست انتخاب کنید.

## اکانت تست

از جزئیات کاربر می‌توان وضعیت او را بین «عادی» و «تست» تغییر داد.

قواعد v6.0.0:

- خریدهای کاربر تست از فروش واقعی و نمودارهای درآمد واقعی حذف می‌شوند.
- شارژها و تراکنش‌های همان کاربر با برچسب تست نگهداری می‌شوند.
- با تغییر وضعیت کاربر، خریدها، شارژها و ledger قبلی او نیز برای گزارش‌گیری دوباره طبقه‌بندی می‌شوند.
- کاربر تست پاداش رفرال جدید ایجاد نمی‌کند.
- معرف تست نیز پاداش رفرال دریافت نمی‌کند.
- خرید تست همچنان یک لینک واقعی از استخر مصرف می‌کند؛ برای آزاد کردن آن باید سرویس به استخر بازگردانده شود.
- تغییر کاربر از عادی به تست، پاداش رفرالی که قبلاً واقعاً پرداخت شده را خودکار پس نمی‌گیرد؛ این مورد باید در صورت نیاز دستی بررسی شود.

پیشنهاد: قبل از هر خرید آزمایشی، کاربر را به حالت تست ببرید.

## کیف پول و رسید

- تأیید و رد رسید به‌صورت اتمیک انجام می‌شود.
- دو ادمین نمی‌توانند یک شارژ را هم‌زمان دو بار تأیید کنند.
- فایل رسید تکراری ثبت می‌شود و تعداد استفاده قبلی آن به ادمین نمایش داده می‌شود.
- سابقه رسید تکراری حذف نمی‌شود تا Audit مالی از بین نرود.
- موجودی کاربر اجازه منفی شدن ندارد.
- تغییر دستی موجودی در ledger و لاگ ادمین ثبت می‌شود.

## رفرال

پاداش فقط وقتی پرداخت می‌شود که:

- کاربر معرفی‌شده اولین خرید واقعی خود را تکمیل کند؛
- کاربر و معرف بن نباشند؛
- هیچ‌کدام اکانت تست نباشند؛
- سقف روزانه و کلی رفرال رد نشده باشد؛
- پاداش قبلاً پرداخت نشده باشد.

پرداخت پاداش داخل تراکنش اتمیک انجام می‌شود تا اجرای هم‌زمان باعث پرداخت چندباره نشود.

### جزئیات کاربر

صفحه اصلی فقط خلاصه مدیریتی را نشان می‌دهد. اطلاعات طولانی به بخش‌های جدا منتقل شده‌اند:

```txt
📦 سرویس‌ها و خریدها
💰 مالی و کیف پول
🎫 تیکت‌ها
👥 رفرال
📝 یادداشت ادمین
💬 ارسال پیام
🧪 وضعیت تست
➕ افزایش / کاهش موجودی
```

لینک کامل فقط در جزئیات همان سرویس نمایش داده می‌شود. ارسال لینک، QR و بازگردانی به استخر نیز داخل همان صفحه قرار دارند.

### مدیریت پلن‌ها

هر پلن می‌تواند تنظیمات مستقل داشته باشد:

- عنوان، حجم و مدت
- قیمت فروش و هزینه خرید اختیاری
- توضیح و برچسب
- فعال/غیرفعال
- ترتیب نمایش
- سقف خرید هر سفارش
- حد هشدار موجودی
- نمایش یا عدم نمایش موجودی
- متن قبل و بعد از خرید

### مدیریت دکمه‌ها و پیام‌ها

- دکمه جدید ابتدا Draft می‌شود.
- پیش‌نمایش قبل از انتشار وجود دارد.
- callback خام یا اجرای کد دلخواه پشتیبانی نمی‌شود.
- عملکرد دکمه‌های سیستمی قفل است و فقط ظاهر، ترتیب و جایگاه آن‌ها تغییر می‌کند.
- پیام‌های دارای `{body}` بخش سیستمی خود را از دست نمی‌دهند.
- متن فعلی و متن پیش‌فرض قابل مشاهده‌اند.

## پاک‌سازی پیام‌ها

پیام‌های ربات با context و نوع ثبت می‌شوند. هنگام باز شدن یک بخش جدید، فقط پیام‌های موقت، منویی، لیستی یا پیش‌نمایش تا جای ممکن جمع می‌شوند.

پیام‌های زیر کورکورانه حذف نمی‌شوند:

- لینک تحویل‌شده
- رسید پرداخت
- فایل بک‌آپ
- پیام مهم

اگر حذف یک پیام ممکن نباشد، ربات تلاش می‌کند کیبورد قدیمی آن را حذف کند و خطا باعث توقف جریان نمی‌شود.

## بک‌آپ و Restore

بک‌آپ شامل خود دیتابیس SQLite است و قبل از Restore بررسی می‌شود:

- SQLite بودن فایل
- `PRAGMA integrity_check`
- وجود جدول‌ها و ستون‌های ضروری
- نسخه Schema
- آمار کاربران، لینک‌ها، خریدها و تراکنش‌ها

قواعد Restore:

- Restore فقط برای Owner مجاز است، اگر `OWNER_ID` تنظیم شده باشد.
- قبل از Restore از دیتابیس جاری بک‌آپ اضطراری گرفته می‌شود.
- فایل ابتدا در مسیر staging بررسی می‌شود.
- جایگزینی دیتابیس اتمیک‌تر انجام می‌شود.
- بک‌آپ با Schema جدیدتر از کد فعلی رد می‌شود.
- عملیات در backup log ثبت می‌شود.

قبل از هر Redeploy یا migration، یک بک‌آپ دستی دانلود کنید.

## دیتابیس و هم‌زمانی

Schema فعلی:

```txt
600
```

بهبودهای v6.0.0:

- `WAL` و `busy_timeout` برای SQLite
- قفل مشترک برای عملیات حساس
- cursor محلی هر Thread برای جلوگیری از خطای recursive cursor
- تراکنش `BEGIN IMMEDIATE` برای خرید، تأیید پرداخت و پاداش رفرال
- indexهای بیشتر برای خرید، لینک، پیام، کاربر و گزارش‌ها
- trigger برای جلوگیری از ورود لینک تکراری در داده‌های جدید
- migration سازگار از v5.6.5

این معماری برای یک Instance ربات و حجم فروش فعلی مناسب است. برای چند Instance هم‌زمان یا بار بسیار زیاد، PostgreSQL و صف Job پیشنهاد می‌شود.

## چک‌لیست Deploy

1. از دیتابیس فعلی بک‌آپ بگیرید.
2. سورس جدید را جایگزین کنید؛ دیتابیس و Environment را overwrite نکنید.
3. Redeploy کنید، نه فقط Restart روی سورس قدیمی.
4. لاگ اجرای اول و migration را بررسی کنید.
5. `VERSION.txt` را داخل محیط Deploy بررسی کنید.
6. یک پلن و لینک تست بسازید.
7. با کاربر تست خرید، پرداخت، تحویل و بازگردانی را امتحان کنید.
8. بعد از تأیید، فروش واقعی را باز کنید.
